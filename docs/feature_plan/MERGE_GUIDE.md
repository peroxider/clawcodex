# 四文档融合指南

## 1 目标

将当前分散在四个文档中的特性信息**融合为一套统一的目录结构**，实现：

- **单一事实源**：每个 F-Number 在一处查阅、一处更新
- **设计 + 进度合一**：特性规划（含详细设计）与开发进度不再分离
- **已完成特性不重复归档**：代码即真理，已实现的特性不再维护文档副本
- **维护成本降低**：新特性和迭代只需修改一处，无需同步四份文档

## 3 融合规则

### 3.1 状态判别原则

融合前需要确认每个 F-Number 的**当前真实状态**，因为三份文档中的状态可能存在冲突。

```
┌────────────────────────────────────────────┐
│  状态判别规则                                │
│                                            │
│  1. 代码存在 + 测试通过 = ✅                │
│     → 删除该 F-Number 的所有文档内容        │
│                                            │
│  2. 代码部分存在 + 正在开发 = 🔄             │
│     → 融合三源内容为一份统一文档             │
│                                            │
│  3. 代码不存在但有详细设计 = 📋             │
│     → 融合三源内容为一份统一文档             │
│                                            │
│  4. 调研阶段/概念验证 = 🔭                 │
│     → 融合三源内容为一份统一文档             │
└────────────────────────────────────────────┘
```

**特殊处理**：

- **F-46** — `PROGRESS.md` 呈 📋 但实际代码已部分完成（headless auto-override 已实现，三字段拆分未完成）。应判定为 🔄。
- **F-70** — `FEATURE_PLAN.md` 同时出现 📋 和 🔄。查代码 `src/plugins/` 8 文件 1,070 行已存在基础框架，应判定为 🔄。
- **F-73** — 标记为 "本地已完成 / 远端待验证"。保留为 🔄，融合进度文档中的实施细节。
- **F-64/F-65/F-67/F-78/F-80/F-88** — 各源状态冲突（有些 ✅ 有些 🔄）。应查代码确认最终状态后统一。

### 3.2 融合规则矩阵

| 源内容类型 | 目标文档位置 | 处理方式 |
|-----------|------------|---------|
| FEATURE_PLAN.md 中的详细设计 | 子文档 §1 设计规划 | 按原文结构搬入，修正状态标记 |
| FEATURE_PLAN.md 中的版本历史（涉及 🔄📋🔭 的条目） | README.md 变更历史 | 摘要式保留，不逐行复制 |
| PROGRESS.md 中的进度详情 | 子文档 §2 进度跟踪 | 融合时按时间顺序整理，标注每项完成的日期/版本 |
| PROGRESS.md 中的子特性/验收标准/风险等结构化字段 | 子文档 §3 实施细节 | 与 FEATURE_PLAN.md 的同字段合并去重 |
| ARCHIVED_PROGRESS.md 中的归档进度 | 子文档 §2 进度跟踪 | 标记为「已归档」段 |
| ARCHIVED_FEATURES.md 的任何内容 | **不搬入，直接删除** | 已完成特性对应代码 |

### 3.3 内容去重规则

融合时同一字段在多个源中出现时：

```
优先级：
  代码状态（查 src/ + clawcodex_ext/ + extensions/ 目录）
  > FEATURE_PLAN.md 设计描述
  > PROGRESS.md 进度描述
  > ARCHIVED_PROGRESS.md 归档描述
```

例如 F-22 的"验收标准"同时出现在 FEATURE_PLAN.md §5.8 和 PROGRESS.md §五中：
- 以 FEATURE_PLAN.md 的设计为准，补充 PROGRESS.md 中新增/修改的条目
- 删除重复项

### 4.2 模板使用说明

- **§1 设计规划** — 核心设计内容。如果 FEATURE_PLAN.md 中已有完整设计，直接搬入、修正状态。如果 PROGRESS.md 中有更新的设计修订，以最新者为准。
- **§2 进度跟踪** — 时间线式记录。✅ 的子特性以小表格呈现完成情况，🔄 的列出当前阻塞点和瓶颈。
- **§3 实施细节** — 结构化字段。从两源合并去重，删除重复/过时的条目。
- **§4 变更记录** — 简明的 git 日志，不需要逐条引用 v3.x 版本变更。

### 4.3 大特性模板扩展（500+ 行的特性）

对于 F-22（Cron）、F-50（SOP 转换器）、F-108（Freeze Detection）、F-110~F-116（工作流引擎）等大特性：

- §1 可以进一步拆分为 §1.x 子节
- 子特性（F-22-A~T）放在 §1.3 子特性分解后，每个子特性一篇 `####` 小节
- 进度跟踪的 §2.1 里程碑可以细分到子特性粒度

## 6 实施步骤

### Step 1 — 准备阶段

1. 创建 `docs/feature_plan/` 目录及子目录结构
2. 创建 `docs/feature_plan/README.md`（主文档）
3. 创建 `docs/feature_plan/01-overview.md`（项目概述）
4. 逐一确认每个 🔄/📋/🔭 F-Number 的当前真实状态（代码 vs 文档对照）

### Step 2 — 融合阶段（逐个 F-Number 执行）

为每个需要保留的 F-Number：

1. 在 `docs/feature_plan/` 下创建目标文件
2. 从 FEATURE_PLAN.md 提取设计内容 → 写入 §1
3. 从 PROGRESS.md 提取进度内容 → 写入 §2
4. 从 ARCHIVED_PROGRESS.md 补充归档进度 → 写入 §2
5. 合并去重结构化字段 → 写入 §3
6. 更新 README.md 中的 F-Number 状态表和目录

### Step 3 — 验证与清理

1. 检查所有 🔄/📋/🔭 F-Number 已覆盖
2. 验证 F-Number 索引无遗漏
3. 原四份文档重命名为 `.legacy.md`
4. 全局 grep 确认无失效的交叉引用

### Step 4 — 后续

1. 在 `CLAUDE.md` 中更新文档路径引用
2. 将所有 `docs/FEATURE_PLAN.md` 的外部引用更新为 `docs/feature_plan/`
3. 删除 `.legacy.md` 文件（确认无引用后）
