01 · 概览

三层结构，每层各司其职

Orchestrator 不绑定特定的 LLM 或 issue 平台。它只做一件事：把已有的 Agent / QueryRunner / Tool System 装进一个长循环，外加一份声明式 workflow.md 配置文件。整个系统分三层——tracker 适配器负责跟平台对话，orchestrator 核心负责状态机和 Git 同步，agent runner 负责让 LLM 写代码。

01

声明式而非命令式

所有行为由一份 workflow.md 描述：tracker、hooks、agent 限制、验证命令——都是 YAML，不必写代码。

02

通用而非绑定

可以接入任何支持 issue + PR 工作流的平台，可以驱动任何能调用工具的 Agent 循环。

03

可观测而非黑箱

每次 run 产出结构化日志、报告双写、issue 评论附状态快照——任何一步都可追溯。

02 · 适配器

五个 Tracker，一套抽象

五个 issue 平台，能力边界各不相同。Orchestrator 不假设它们等价——同一个 TrackerAdapter 协议下，每个平台以自己的方式实现，不支持的能力就老老实实标注 —。下面这张矩阵就是诚实的能力清单。

Tracker 能力矩阵 覆盖 issue/comments/PR/评论扫描/Inline review/CI status/Push/Intent labels 9 个维度 GitHub/Gitee/GitCode = 9/9 完整
TrackerAdapter · ABC + 默认方法 · 旧实现无需 override 5 个实现 · 9 项能力维度

几个值得拎出来说的细节：

  • Linear 没 PR API。所以它只占 2/9——它做 issue 跟踪，最后需要 GitHub/Gitee/GitCode 来开 PR。
  • Local tracker 不发远端。这是设计行为，不是失败——issue 终态固定 PENDING_REVIEW，分支留在 workspace 等人工接管。
  • 三个 REST 平台覆盖 9/9。任何需要 PR 自动化的项目都能开箱即用。

整个 pipeline 的关键拐点在 stage 9——验证门控。任何 test_command / build_command / lint_command 失败，commit 保留，push 阻断，issue 标记为 verification_failed。这一步把「能跑通」从 agent 的自觉变成了 orchestrator 的硬约束。

— 验证门控是整个 pipeline 唯一会阻断 push 的阶段
04 · 验证门控

三道关卡，pre-push 之前全部要过

在 push 之前插入三道验证关卡：先 test_command，再 build_command，最后 lint_command。任一失败抛 VerificationFailed，阻断 push 但保留 commit，方便排查。报告同时双写到 workspace 的 .reports/ 和用户全局报告目录。

多语言验证门控 · 5 种生态切换 Python · Node.js · Go · Rust · Java · 任选一种查看对应的 test/build/lint 命令 切换语言 · ▶ Run · ✕ Fail
验证失败抛 VerificationFailed · HookFailedError(hook_name) · orchestrator 捕获后标 verification_failed 3 commands · sequential · 600000ms timeout each

几个设计取舍：

  • 失败保留 commit。不 reset，不回退——失败的现场留给调试，commit 历史保持线性。
  • 空字符串 = 跳过。这不是判断逻辑，而是默认配置。空配置语义 = 「不验证」，而不是「验证必须通过」。
  • 语言无关。三道命令是任意 shell 字符串，不绑定任何特定工具链。Python / Node / Go / Rust / Java 都可，开箱即用。
  • 报告双写。workspace 内一份（随 commit 走），用户全局一份（持续累积）。无论成败都写。
05 · 反馈闭环

PR 上的每一条评论，都能变成下一个 commit

这是独立于 issue polling 的另一条循环——它扫描已开 PR 的 review comments 和 CI 失败信号，调度一次 follow-up agent run。关键点：复用同一个分支，commit 前缀 fix: 而不是 feat:，PR body 重新渲染一次。最多 5 轮，耗尽就停止。

反馈闭环动画 7 个节点：PR with feedback → poll → schedule → agent fix → commit → reply → 闭环判断 ▶ Run Follow-up Cycle
git_sync.sync(mode="followup") · commit 加 fix: 前缀 · PR body 重新渲染 max followup attempts per PR = 5 · ignore_authors 黑名单

这条循环解决的真正问题是 PR 的二阶生命周期。一个 PR 开出来不算结束——它要被 review、要修 lint、要修测试、要响应反馈。把这些零散的「再跑一次」收纳成一条自动闭环，直到 PR 真正被合并或被放弃。

06 · 操作员意图系统

四个标签，覆盖人类想干预的所有理由

Operator 介入的方式不需要写脚本——给 issue 加个 label 就行。这里定义了四种 intent，按优先级 blocked > rebase > followup > retry > none 解析。点击下面的标签可以模拟不同的 operator 决策。

Intent 决策树交互 左：点击 issue 标签模拟 · 右：高亮匹配的优先级路径与最终解析结果 点击标签试试
Intent 枚举 · DEFAULT_INTENT_LABELS 标签映射 · intent_from_label_set() 解析 P1 blocked · P2 rebase · P3 followup · P4 retry

为什么这个优先级序列值得专门设计？

  • blocked 永远胜出。一旦标了 agent:blocked，issue 永久跳过——这是「停掉」语义，最强。
  • rebase 比 retry/followup 更高。rebase 触及远端历史，比 followup 的「追加 commit」更激进，所以优先级更高。
  • followup 比 retry 更保守。retry 关旧 PR + 新 PR；followup 保留 PR 证据 + 追加 commit。前者破坏可追溯性。
07 · 性能基线

性能也是产品的一部分

整个流水线有六个关键性能维度可以监控：tracker 轮询延迟、agent 冷启动、tool 调用吞吐、验证门控时长、端到端 issue 到 PR 时长、push 到 PR URL 耗时。所有指标都有默认阈值，CI runner 通常慢 2-3 倍，所以 CI 上的阈值会按倍数放宽。

08 · 实战

一份完整可跑的 workflow.md（Python 示例）

把上面所有特性落到一份文件里——下面是一个 Python 项目的 workflow 实例。YAML frontmatter 是配置，markdown body 是 agent 看到的 prompt 模板，每条 {{…}} 占位符在每次 run 时渲染。验证命令可替换为任何语言生态的对应命令（见上一节的 5 种 preset）。

workflow.md yaml + markdown · Python 示例 
---
tracker:
  kind: github
  owner: myorg
  repo: myrepo
  api_key: $GITHUB_TOKEN
  active_states: [open]

polling:
  interval_ms: 30000

workspace:
  strategy: isolated
  base_branch: main
  gitignore_patterns:
    - .reports
    - .venv

agent:
  max_concurrent_agents: 5
  max_turns: 30
  permission_mode: dontAsk  # orchestrator 自动升级为 bypassPermissions

  # 验证门控 · Python 生态示例（也可配 Node/Go/Rust/Java）
  test_command: "python3 -m pytest tests/ -x -q"
  build_command: "uv build"
  lint_command: "uv run ruff check ."

  # 429-aware 退避
  rate_limit_base_delay_ms: 30000
  rate_limit_max_backoff_ms: 600000
  rate_limit_max_retries: 5

hooks:
  after_create: "uv sync --frozen"
  pre_commit: "uv run black --check . && uv run black ."
  timeout_ms: 120000

followup:           # PR 评论反馈闭环
  enabled: true
  mode: auto
  poll_interval_ms: 60000
  max_attempts_per_pr: 5

observability:
  dashboard: extensions/orchestrator/status_dashboard.py
---

# Orchestrator Agent Prompt

你正在处理 issue {{ issue.identifier }} · {{ issue.title }}

## 任务背景
{{ issue.body }}

## 工作环境
- 工作目录: {{ workspace.path }}
- 基础分支: {{ workspace.base_branch }}
- Issue 分支: {{ workspace.branch_name }}

## 约束
1. 只改与本 issue 直接相关的代码
2. 跑 workflow.md 中配置的 `test_command` 验证（默认 Python 生态示例：pytest）
3. 跑 workflow.md 中配置的 `lint_command` 确认无 lint 错误（默认 Python 示例：ruff）
4. 提交信息遵循 conventional commits 规范

完成后报告修改的文件清单与测试结果。

把它放进 repo 根目录的 workflow.md，跑：

terminal bash 
$ orchestrator server start --workflow ./workflow.md

守护进程启动后，按 polling.interval_ms 周期拉取 issue，看到匹配的 label 自动派出 agent，全程无需人类介入直到 PR 被开出来。
